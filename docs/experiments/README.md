## 실험 사이의 흐름

1. **파일럿**은 운영 클러스터 노드 하나를 비우고 Iris를 1→30대로 늘렸습니다.
   제출 프로세스가 pod cgroup 밖(`/sandbox-*`)에서 모든 CPU를 쓴다는 사실을
   발견했습니다.
2. 파일럿 뒤 server8은 클러스터에서 분리되어 벤치마크 전용 호스트가 되었고,
   이 레포의 도구(봉인된 실행 계획, 에이전트, 증거 번들)가 만들어졌습니다.
3. **1차**는 Judger만 떼어 같은 경향을 재현했습니다. **2차**는 운영 Iris
   이미지와 RabbitMQ·RDS·S3 경로를 다시 넣어도 결과가 같음을 확인했습니다.
4. **3차**는 보안 패치용 Go 교체가 이 기준선을 바꾸지 않는지 확인했습니다.
5. **4차**는 하드웨어 카운터로 원인을 나눴습니다. 계산 위주 코드는 터보와 SMT,
   메모리 위주 코드는 L3·대역폭·NUMA가 지배합니다.
6. **RDT 관측**과 **CAT A/B**는 4차의 캐시·대역폭 가설을 레포 도구로 다시
   확인하기 위한 예비 실험입니다.

## 공통 주의 사항

- 모든 결과는 `production-compat`이며 `comparable=false`입니다. alpha.4
  Judger가 제출을 호스트 루트 `/sandbox-*` cgroup에 넣기 때문입니다. 같은
  실험 안의 단계끼리만 비교하고, 다른 모집단과 절대값을 합치지 않습니다.
- 측정 호스트는 server8(`skkuding-4f-4`, SSH 별칭 `codedang8`) 한 대입니다.
  Xeon E5-2620 v4 2소켓, 16코어/32스레드, 소켓당 L3 20 MiB입니다. DIMM 배치가
  비대칭이라(socket0 32 GiB, socket1 16 GiB) 메모리 대역폭이 소켓마다 다릅니다.
- 주요 통계는 모든 워커가 동시에 활성인 **정상 상태 구간**의 표본만 씁니다.
  구간은 `[워커별 첫 시작의 최댓값, 워커별 마지막 종료의 최솟값]`입니다.
- 원본 번들(`runs/`)은 Git에 없습니다. 실험을 수행한 운영자 머신과 server8에
  남아 있습니다. 각 실험 문서의 "산출물" 절을 보세요.
